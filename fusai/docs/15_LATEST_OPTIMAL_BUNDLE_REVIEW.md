## 4. v28 的真实技术路线

v28 是自包含脚本，直接读取官方一分钟数据并完成 15 分钟取点、特征、192 个 LightGBM、燃料回归、融合和打包。其关键变化是：

1. 恢复 `blast_furnace_3`、`air_heater_3`、`air_heater_5`、`converter_user1`。
2. `blast_furnace_3` 缺失按“停炉即 0”填充。
3. 继续排除常量 `converter_user3` 和数值损坏的 `blast_furnace_gas_holder_1`。
4. `generator_1` 树只用 9 月起点；`generator_all` 树用全期起点。
5. 两个目标都加入 9 月燃料线性映射；远期 `generator_all` 还混合起点星期/小时气候项。
6. 虽然代码计算了 `fire` 和 `gate_scale`，v28 实际没有把 gate 应用于输出；它是 no-gate 版本。

实际融合公式以代码为准。这里存在一个必须保留的语义细节：循环变量 `h_step` 的值是分钟数 15、30、45……，但代码判断 `h_step <= 32`。所以文档所称“近端 32 步”实际上只覆盖 **15 和 30 分钟两个 horizon**，不是第 1–32 步。

- g1：15/30 分钟燃料权重 0.8，其余 horizon 为 0.6；
- gall：15/30 分钟为 0.5 tree + 0.5 fuel；其余为 0.225 tree + 0.075 origin-climatology + 0.70 fuel。

这一实现应在复现阶段原样保留；若改成真正的 32 步，应另立实验，不能称为 v28 复现。

## 5. 文档、manifest 与源码的不一致

静态审阅发现以下问题，后续必须以代码和哈希为最高优先级：

1. v28 模块 docstring 仍称 v27。
2. v28 manifest 写 g1 权重 0.8→0.7，实际代码是 0.8/0.6。
3. v28 manifest 称 gall 含 gate，实际 gate 只计算未应用。
4. v34 manifest/docstring 保留了旧描述；实际权重是 15/30 分钟 0.6，其余 0.1，并加入 g1 异常样本权重。
5. `复现验证总表.md` 把 v28 标成待提交，而 README 又明确写官方 61.5824，前者显然是未同步旧记录。
6. README 称每个候选目录都有 manifest，但 v29b 目录没有 manifest。
7. README 的 v29b 命令链不能从该包独立产生所需 v20 中间产物。
8. v28 manifest 的 Git 状态为 dirty；提交哈希本身不足以恢复当时工作区，必须保留本次源码快照。

这些问题不否定 v28 成品分数，但说明作者侧“全部可字节复现”的承诺尚不能替代本项目的独立重建。
