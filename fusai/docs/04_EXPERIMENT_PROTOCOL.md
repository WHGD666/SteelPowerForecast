# 实验管理协议

## 1. 实验角色

每个 run 必须属于以下一种角色：

| 角色 | 目的 | 可否成为提交候选 |
|---|---|---|
| diagnostic | 理解数据、泄漏、上界和失败机制 | 否 |
| scientific | 在固定协议下比较一个假设 | 通过合规检查后可以 |
| competition | 使用全部规则允许信息构建候选 | 可以 |
| final | 已冻结、准备复现和提交 | 可以 |

## 2. 一次只改变一个主要因素

正式实验必须先写清：

- 控制组 run_id。
- 假设。
- 唯一主要变化。
- 预期影响哪个目标、哪个预测区间。
- 成功判据。
- 失败后的决策。

不允许在一次实验中同时更改标签、切分、异常处理、特征组、模型参数、融合和后处理，再把最终变化归因给其中某一项。

## 3. run_id

推荐格式：

```text
YYYYMMDDTHHMMSS_<task>_<experiment>_<short-hash>
```

示例：

```text
20260930T103000_short_g1_interval_labels_a1b2c3d4
20260930T150000_long_holiday_features_e5f6g7h8
```

run_id 一经创建不得复用。重跑、修复或换 seed 都是新 run。

## 4. 每个 run 必须保存

- `run_manifest.yaml`：运行身份、协议、哈希、环境、命令和状态。
- `resolved_config.yaml`：完整解析后的配置。
- `metrics.json`：机器可读总体和分层指标。
- `metrics_by_horizon.csv`：每目标、每步长、每折指标。
- `oof_predictions.*`：验证预测，格式后续冻结。
- `feature_contract.json`：允许字段、派生字段和来源时间定义。
- `events.log`：开始、完成、失败和关键阶段。
- 模型文件或模型重建说明。
- 失败时的异常类型、信息和最后成功阶段。

## 5. 实验登记簿

`experiments/round2_v3/registry.csv` 是唯一机器可读索引，只追加，不手工覆盖历史行。

`EXPERIMENT_LOG.md` 保存人类可读结论。任何“最好”“提升”“失败”的描述都必须指向 run_id。

禁止在多个 README 中手工维护互相冲突的最好分数。

## 6. 可比较性

只有同时满足以下条件的两个 run 才能直接声称提升：

- protocol_version 相同。
- label_version 相同。
- split_fingerprint 相同。
- metric_version 相同。
- feature availability contract 相同。
- 缺失和异常处理规则相同，或变化正是被研究的唯一因素。
- 使用同样的 OOF 聚合方式。

旧 v2/v9 与新 v3 可以比较官方平台结果，但不能直接比较本地 MAPE。

## 7. 实验族优先级

建议按以下次序推进：

1. 正确标签和验证 baseline。
2. 异常处理、部分投运字段和物理平衡修复。
3. 短周期专用特征与机理残差。
4. `generator_1` / 大机组残差层次模型。
5. 目标时刻日历与国庆工况特征。
6. 长周期未来煤气路径预测。
7. CatBoost、LightGBM 等模型族比较。
8. OOF 融合和校准。
9. 深度时序模型作为互补成员。

先证明实验族有效，再进行小规模参数搜索。

## 8. 失败实验

失败同样是正式记录。需要填写：

- 假设为什么失败。
- 是数据、实现、算力、验证还是模型原因。
- 是否存在可复用的回归测试。
- 是否停止该路线。
- 后续是否允许重试以及重试条件。

不得删除低分 run 或只保留成功结果。

## 9. 平台反馈的使用边界

平台每日最多五次提交，适合验证少量高价值假设，不适合随机搜索。

- 每次只替换短文件或长文件中的一个主要组成部分。
- 保持另一文件冻结以隔离影响。
- 记录 ZIP 哈希、上传时间和所有平台明细。
- 不根据细小分差反复手调测试预测。
- 不通过提交构造反推测试标签。

## 10. 采用或拒绝标准

一项改动只有满足以下条件才进入下一候选：

- 合规。
- OOF 主指标改善或提供必要的稳定性收益。
- 多数验证折方向一致。
- 没有以明显损害 `generator_all` 换取有限 g1 增益。
- 物理违规不增加。
- 运行和复现成本可接受。
